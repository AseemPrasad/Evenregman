# 🛠️ Operations & Incident Runbooks (SRE Guide)

This document provides actionable runbooks, diagnostic commands, and recovery procedures for site reliability engineers (SREs) managing production clusters.

---

## Runbook 1: Redis Crash or Cold-Start Capacity Desynchronization

### 1.1 Symptoms
* Prospective attendees receive "This event is sold out" errors even though MongoDB displays available seats.
* Or, users are able to register beyond physical venue capacity after a sudden Redis reboot.

### 1.2 Root Cause
Redis restarted with cold or volatile memory, leaving key `event:{eventId}:capacity` uninitialized or out-of-sync with MongoDB's persistent `attendeeCount`.

### 1.3 Remediation Procedure
1. Execute the manual counter synchronization script via Node CLI or internal admin console:
   ```typescript
   import { redisSyncEventCapacity } from "@/lib/redis-operations";
   import { EventModel } from "@/models/Event";
   import { connectToDatabase } from "@/lib/db";

   async function resyncAllEvents() {
     await connectToDatabase();
     const openEvents = await EventModel.find({ status: { $in: ["OPEN", "FULL"] } });
     for (const ev of openEvents) {
       const remaining = Math.max(0, ev.capacity - ev.attendeeCount);
       await redisSyncEventCapacity(ev._id.toString(), remaining);
       console.log(`Synced ${ev.slug}: ${remaining} seats available`);
     }
   }
   ```
2. Verify Redis counter status:
   ```bash
   redis-cli GET "event:<eventId>:capacity"
   ```
3. Purge L2 cache tags:
   ```bash
   curl -X DELETE http://localhost:3000/api/metrics/cache
   ```

## Runbook 2: Poison-Pill Outbox Events & Dead-Letter Queue Triage

### 1.1 Symptoms
* The metrics endpoint `/api/metrics/outbox` reports an increasing number of events in `status: "FAILED"`.
* Users report not receiving confirmation emails or S3 export notifications.

### 1.2 Investigation
1. Query dead-letter events in MongoDB:
   ```javascript
   db.outbox_events.find({ status: "FAILED" }).sort({ updatedAt: -1 }).limit(10);
   ```
2. Inspect the `error` field on the failed documents:
   - If error is `ETIMEDOUT` on SMTP host: Verify outbound firewall port `587` is open.
   - If error is `SignatureDoesNotMatch` on AWS S3: Verify system clock skew (`ntpdate`) and IAM credentials.

### 1.3 Replay Procedure
Once the underlying infrastructure issue is resolved, reset failed events to `PENDING` to trigger immediate reprocessing:
```javascript
db.outbox_events.updateMany(
  { status: "FAILED", eventType: "REGISTRATION_CREATED" },
  {
    $set: {
      status: "PENDING",
      retryCount: 0,
      scheduledAt: new Date(),
      updatedAt: new Date()
    }
  }
);
```

## Runbook 3: MongoDB Oplog Rollover Recovery (CDC Stream Lost)

### 1.1 Symptoms
* Real-time dashboard analytics charts stop updating.
* Worker logs display: `MongoServerError: ChangeStreamHistoryLost: Resume token was not found in the oplog`.

### 1.2 Root Cause
A massive spike in database writes filled the fixed-size MongoDB replication oplog, evicting the cursor position stored by `cdcResumeTokenService`.

### 1.3 Automatic vs Manual Recovery
* **Automatic Behavior**: The built-in error handler in `src/workers/cdc-worker.ts` automatically catches error code `286` (`ChangeStreamHistoryLost`), purges the stale resume token from Redis, and reconnects to the head of the oplog.
* **Manual Force Reset** (if worker is stuck):
  1. Clear the resume token key in Redis:
     ```bash
     redis-cli DEL "cdc:resume_token:registrations"
     ```
  2. Restart the worker container:
     ```bash
     docker compose restart worker
     ```

## Runbook 4: Pre-signed S3 URL Expiration during Long Downloads

### 1.1 Symptoms
* A host begins downloading a massive CSV export 20 minutes after generation and receives an AWS S3 `Request has expired` XML error.

### 1.2 Explanation & Architecture Safeguard
AWS SigV4 pre-signed URLs generated by `@aws-sdk/s3-request-presigner` carry a hard 15-minute (900s) cryptographic validity window for security compliance.

### 1.3 Resolution (Built-in Just-In-Time Refresh)
The host does not need to re-run the entire export job!
1. The host simply revisits or polls `/api/jobs/[jobId]`.
2. The endpoint detects that `job.status === "completed"` and automatically executes:
   ```typescript
   downloadUrl = await generatePresignedUrl(job.s3Key, 900);
   ```
3. A fresh, valid 15-minute pre-signed URL is generated instantaneously from the stored `s3Key` without re-querying the database or regenerating the CSV file.
